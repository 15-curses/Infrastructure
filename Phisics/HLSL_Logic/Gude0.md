# Полный пайплайн кадра

```
MoveKernels → IntegrateObjectMovement → MortonKernel → RadixSort
   → CS_InitBVHLeafBounds → BVH_Main (N итераций, между ними CS_FinalizeBVHIterationArgs)
   → CS_TraverseBVH → GJK / СontactСheck → ComputePhysicsResponse
```

> ⚠️ **Открытый вопрос (не решён):** является ли `ObjectBuffer` плотным (dense) или в нём
> есть "дыры" из-за free-list аллокатора (`AddBuffersLogic.hlsl` / `GetFreeIndex`/`AddFreeIndex`)?
> От ответа зависит, нужна ли компакция через `In_ActiveObjectIndices` перед broadphase,
> или можно безопасно считать `idx == realObjId`. Пока это не зафиксировано — рассматривайте
> шаги ниже, работающие с "плоским" диапазоном ObjectCount, как потенциально требующие
> дополнительного слоя индирекции.

---

## 1) Start MoveKernels

CPU вызывает диспетчеризацию (dispatch) для вычислительных шейдеров (кернелов), отвечающих за
перемещение объектов. Количество рабочих групп (thread groups) для каждого кернела рассчитывается
путем округления числа обрабатываемых им объектов до ближайшего большего числа, кратного 32
(размер развертки/варпа).

Параллельно CPU подсчитывает суммарное количество объектов, перемещаемых всеми кернелами вместе.
Это общее число также округляется до ближайшего кратного 32 и делится на 32. Полученное значение
(количество необходимых групп) записывается в буфер indirect-аргументов для непрямого вызова
(`DispatchIndirect`) шейдера Morton на этапе [MortonKernel](#3-mortonkernel).

> ⚠️ **Важно:** это значение должно попадать в **отдельный** буфер indirect-аргументов
> (аналог `IndirectArgsBuffer`/`BVHIndirectArgs`), а **не** в нулевой слот `MovedObjectCounter`.
> `MovedObjectCounter[0]` — это атомарный счётчик записи (`InterlockedAdd` внутри `AddMovedObject`,
> см. `Pops.hlsl`), он обязан стартовать с 0 перед `MoveKernels`, иначе индексация записи в
> `MovedObjects` собьётся. Число групп для indirect-диспетчеризации Morton нужно держать в
> отдельном слоте/буфере, который CPU заполняет заранее.

## 2) MoveKernels

Каждый вычислительный шейдер (kernel) по собственной математической модели рассчитывает новую
позицию объекта, а также его линейную и угловую скорости. После этого данные обо всех перемещенных
объектах записываются в буфер `MovedObjects`. Индексация в буфере реализуется через атомарный
счетчик `InterlockedAdd` (функция `AddMovedObject`, буфер-счётчик `MovedObjectCounter`).

Запись производится в следующем формате:

```hlsl
struct Object {
    AABB bounds; // Ограничивающий объем объекта (задан min и max координатами по X, Y, Z)
    uint objId_InGlobalBuffer; // Индекс в глобальном буфере объектов (модифицируется только на стороне CPU)
};
```

## 3) IntegrateObjectMovement

Отдельный шаг физической интеграции (Symplectic Euler), выполняется **после** MoveKernels и
**до** Morton — обновляет позицию, вращение и мировой AABB каждого активного объекта
(`IntegrateObjectMovement.hlsl`).

1. **Отсев статики/сна:** если `obj.mass <= 0` или `obj.updateMask == 0` — объект пропускается.
2. **Внешние силы и демпфирование:** к скорости добавляется `Gravity * DeltaTime`; линейная и
   угловая скорости домножаются на коэффициенты затухания, зависящие от `staticFriction` /
   `dynamicFriction`.
3. **Линейное движение:** вычисляется мировой центр масс **до** перемещения
   (`worldMassCenter = position + massCenter * currentRotMatrix`), затем к нему добавляется
   `velocity * DeltaTime`.
4. **Угловое движение:** строится кососимметричная матрица `deltaRotation` из `angularVelocity`,
   новая матрица вращения получается как `R_new = R_old + R_old * [w]x * dt`, после чего
   выполняется ортонормализация строк методом Грама-Шмидта.
5. **Пересчёт позиции:** новая мировая позиция pivot-точки объекта восстанавливается из
   обновлённого центра масс и новой матрицы вращения; итоговая матрица `transform` (4x4,
   row-major) собирается заново.
6. **Обновление мирового AABB:** локальный неизменяемый AABB (`minAABB`/`maxAABB` — шаблон
   объекта) трансформируется в мировые координаты через `TransformAABB` (алгоритм Джима Арво —
   без явного поворота всех 8 вершин), результат сохраняется обратно в `obj.minAABB`/`obj.maxAABB`
   и используется дальше как источник данных для broadphase.

Этот шаг — единственное место, где обновляется `AABB`, попадающий позже и в grid-based broadphase
(`UpdateChunkIDsForAABB`), и в BVH-пайплайн (через `MovedObjects[...].bounds`, заполняемый
`AddMovedObject` из MoveKernels, либо напрямую из обновлённого `ObjectBuffer` в
`CS_InitBVHLeafBounds` — см. ниже).

## 4) MortonKernel

Каждый поток вычисляет свой глобальный индекс через семантику `SV_DispatchThreadID`. По этому
индексу поток считывает данные объекта (его AABB) из буфера `MovedObjects`, заполненного на
предыдущих этапах. Далее для каждого объекта выполняются следующие операции:

1. **Вычисление центра AABB:** находится средняя точка между минимальной (min) и максимальной
   (max) координатами объекта:
   $$\text{Center} = (\text{min} + \text{max}) \times 0.5$$

2. **Генерация кода Мортона:** полученные координаты центра передаются в алгоритм Мортона (см.
   [Алгоритм Мортона (Z-кривая)](#алгоритм-мортона-z-кривая)) для расчета одномерного индекса
   (Morton code), который будет использоваться для пространственного упорядочивания объектов на
   этапе [RadixSort](#5-radixsort).

3. **Запись в буфер:** результат записывается в буфер `Out_MortonPairs` в формате следующей
   структуры:
```hlsl
struct MortonPair {
    uint mortonCode; // Рассчитанный код Мортона
    uint objectID;   // Исходный глобальный индекс объекта
};
```

## 5) RadixSort

LSD (Least Significant Digit) поразрядная сортировка пар `MortonPair` по возрастанию
`mortonCode`, реализована тремя последовательными кернелами (`Pops.hlsl`), обрабатывающими
4-битные разряды (`BITS_PER_PASS = 4`, `NUM_BUCKETS = 16`) за проход. Для 32-битного кода Мортона
требуется до 8 таких проходов, каждый со своим сдвигом `BitShift` (0, 4, 8, ... 28), передаваемым
через `SortSettings`.

Один проход состоит из трёх этапов:

1. **`CS_Upsweep`** — каждый блок из 256 потоков (`THREADS_PER_BLOCK`) строит локальную
   гистограмму по 16 корзинам (`s_Histogram`, groupshared) для своего диапазона элементов.
   Подсчёт внутри блока ускорен wave-интринсиками (`WaveActiveCountBits`, `WaveIsFirstLane`) —
   агрегация идёт на уровне волны/варпа, а не поэлементным `InterlockedAdd`. Результат каждого
   блока пишется в `BlockHistograms` с раскладкой `[Корзина][Блок]`.

2. **`CS_Scan`** — вычисляет эксклюзивный префиксный скан по всей таблице `BlockHistograms`
   (`TotalBlocks * NUM_BUCKETS` элементов), используя Kogge-Stone/Hillis-Steele скан внутри
   групп по 256 элементов и аккумулятор смещения между итерациями цикла. Благодаря раскладке
   `[Корзина][Блок]` линейный скан сразу даёт корректную семантику: результат для
   (корзина `d`, блок `b`) = сумма всех корзин `< d` по всем блокам + сумма корзины `d` в
   блоках `< b`. Результат — `GlobalOffsets`, финальные стартовые адреса для каждой пары
   (корзина, блок).

3. **`CS_Downsweep`** — каждый поток повторно читает свой элемент, определяет корзину
   (`(sortKey >> BitShift) & 0xF`), вычисляет свой локальный ранг внутри волны через
   `WavePrefixCountBits`, затем синхронизирует смещения между волнами внутри блока через
   groupshared `s_WaveOffsets`, и наконец пишет элемент в `OutputBuffer` по адресу
   `s_BlockOffsets[bucket] + localRank + intraWaveOffset`.

После всех проходов `OutputBuffer` содержит `objectID`, отсортированные по возрастанию Morton-кода
— этот порядок используется дальше как `In_ActiveIndices` для инициализации листьев BVH.

## 6) BVH

### 6.1) CS_InitBVHLeafBounds

Отдельный кернел, выполняется **один раз перед** первой итерацией `BVH_Main` для каждого нового
PLOC-билда. Копирует AABB-границы и `objectId` из `ObjectBuffer` в листовые ноды дерева BVH
(индексы `0..N-1`), подготавливая их к первой итерации слияния. Явная инициализация в отдельном
кернеле (а не только "по требованию" внутри `BVH_Main`, как раньше) устраняет гонки при повторных
запусках builda в рамках одного кадра.

### 6.2) BVH_Main — инициализация листа (первая итерация)

Внутри `BVH_Main` (см. ниже) есть отдельная ветка, срабатывающая под guard'ом
`myNodeIdx < ObjectCount_PLOCSettings`: если текущая активная нода — это ещё не построенный
внутренний узел, а исходный лист, то заполняются поля:

```hlsl
BVHNodes[myNodeIdx].isLeaf     = 1;
BVHNodes[myNodeIdx].leftChild  = myNodeIdx;      // objectId листа (поле leftChild переиспользовано)
BVHNodes[myNodeIdx].rightChild = 0xFFFFFFFFu;
BVHNodes[myNodeIdx].parent     = 0xFFFFFFFFu;
BVHNodes[myNodeIdx].bounds     = MovedObjects[myNodeIdx].bounds;
```

Экономия памяти: `objectId` листа хранится в поле `leftChild` (у листа `rightChild` в этом
использовании не нужен), что экономит 4 байта на ноду. **Важно:** `leftChild/rightChild == 0`
нельзя использовать как признак листа — 0 является валидным индексом ноды; поэтому лист
однозначно определяется только явным флагом `isLeaf`.

### 6.3) BVH_Main — поиск ближайшего соседа (Nearest Neighbor)

1. Вычисляем номер активного объекта по `SV_DispatchThreadID`.
2. Получаем индекс текущей ноды в дереве через `In_ActiveIndices[currentActiveIdx]`.
3. Задаём окно поиска (`SearchWindow`, обычно 16–32) **по позиции в отсортированном по Мортону
   активном списке** `In_ActiveIndices`, а не напрямую по значению кода Мортона — массив уже
   упорядочен предыдущей сортировкой, поэтому соседство по индексу приближённо соответствует
   пространственной близости.
4. Ограничиваем окно границами `[0, ActiveCount - 1]`.
5. Для каждого кандидата в окне считаем площадь объединённого бокса (`MergeAABB` +
   `GetSurfaceArea`, метрика SAH) и запоминаем кандидата с минимальной площадью как
   `bestNeighborActiveIdx`.

### 6.4) BVH_Main — взаимное слияние (Mutual Nearest Neighbor)

1. Записываем индекс ноды в локальный кэш `SharedNodeIndices` и ID идеального соседа в
   `SharedBestNeighbors` (groupshared-массивы на группу из 64 потоков).
2. Вызываем `GroupMemoryBarrierWithGroupSync` для синхронизации потоков группы.

**Вариант I: сосед внутри нашей группы потоков**
1) Читаем выбор соседа из быстрой LDS-памяти (`SharedBestNeighbors[neighborLocalIdx]`).
2) Проверяем взаимность: сосед должен был выбрать наш глобальный `currentActiveIdx`.

**Вариант II: сосед за пределами группы (на стыке блоков)**
1) Достаём ограничивающую коробку соседа напрямую из дерева (`BVHNodes[globalNeighborNodeIdx]`).
2) Проверяем, выберет ли этот сосед нас в ответ.
3) Встаём на место соседа для проверки: пересчитываем его окно поиска (`nStart`..`nEnd`) вокруг
   `bestNeighborActiveIdx`.
4) Сканируем это окно и находим `neighborsBestChoice` — минимум площади объединения с точки
   зрения соседа.
5) Если `neighborsBestChoice == currentActiveIdx` — взаимность доказана.

### 6.5) BVH_Main — создание родительской ноды

Если взаимность подтверждена (`isMutualMatch == true`), физически создаёт родителя **только**
поток с меньшим `currentActiveIdx` из пары (чтобы избежать дублирования):

1. Атомарно выделяется индекс новой внутренней ноды из общего счётчика (стартует с `N`):
   `GlobalCounters.InterlockedAdd(0, 1, newParentNodeIdx)`.
2. Строится `parentNode`: `bounds = MergeAABB(детей)`, `leftChild`/`rightChild` = индексы двух
   объединяемых нод, `parent = 0xFFFFFFFF`, `isLeaf = 0`. Нода записывается в `BVHNodes`.
3. Обоим детям (`nodeA`, `nodeB`) проставляется `parent = newParentNodeIdx`.
4. Новая нода добавляется в список активных нод **следующей** итерации:
   `GlobalCounters.InterlockedAdd(4, 1, nextActivePos)`, `Out_ActiveIndices[nextActivePos] = newParentNodeIdx`.

"Проигравшая" сторона пары (`currentActiveIdx > bestNeighborActiveIdx`) ничего не делает — родитель
уже добавлен другим потоком, сама нода в следующий список не попадает.

Если пара **не взаимна** (`isMutualMatch == false`), нода просто переносится в список активных
нод следующей итерации без изменений: `Out_ActiveIndices[nextActivePos] = myNodeIdx`.

### 6.6) CS_FinalizeBVHIterationArgs

Однопоточный (`[numthreads(1,1,1)]`) кернел, запускается между каждой парой итераций `BVH_Main` —
управляет продолжением/остановкой цикла PLOC-билда и подготавливает indirect-аргументы для
следующего запуска:

1. Читает `nextActiveCount` из `GlobalCounters`, байт 4 (счётчик активных нод, накопленный только
   что завершившейся итерацией `BVH_Main`).
2. **Если `nextActiveCount <= 1`** — дерево схлопнулось до одного узла (либо изначально было
   0–1 объектов в сцене):
   - если `nextActiveCount == 1`, читает единственный оставшийся индекс из `Out_ActiveIndices[0]`
     (того же буфера, куда только что писал `BVH_Main`) и записывает его как
     `RootNodeIndexBuffer[0]` — итоговый корень дерева, который позже читает `CS_TraverseBVH`
     напрямую как SRV, без единого readback на CPU за весь кадр;
   - обнуляет `BVHIndirectArgs[0]` (threadGroupsX) — это стоп-сигнал: следующий
     `DispatchIndirect(BVH_Main)` не выполнит ни одного потока, что предотвращает бесконечное
     самокопирование последней активной ноды при `ActiveCount == 1`.
3. **Иначе** — рассчитывает `BVHIndirectArgs[0] = (nextActiveCount + 63) / 64` (число групп для
   следующей итерации `BVH_Main`).
4. `BVHIndirectArgs[1]` и `[2]` всегда `1`.
5. Переносит "next" в "current" для следующей итерации: `GlobalCounters.Store(8, nextActiveCount)`,
   и обнуляет счётчик "next" под накопление в предстоящей итерации: `GlobalCounters.Store(4, 0)`.

> **Требование к буферу:** `GlobalCounters` должен занимать минимум 12 байт (адреса 0, 4, 8).
> Байт 8 (стартовое `ActiveCount == N`) CPU обязан инициализировать перед самым первым кадром/
> первым запуском `BVH_Main`.

## 7) BVH Traversal (Обход дерева)

Процесс обхода иерархии ограничивающих объемов реализован в Compute Shader (`CS_TraverseBVH`) и
устроен следующим образом:

1. **Идентификация потока:** каждый поток вычисляет свой уникальный глобальный индекс через
   `SV_DispatchThreadID.x`. Этот индекс соответствует конкретному объекту (листу дерева), для
   которого ищется коллизия.
2. **Подготовка данных:** по полученному индексу поток извлекает из буфера `In_BVHNodes` исходные
   данные «своего» объекта: ограничивающий бокс (AABB) и идентификатор объекта, который на уровне
   листьев временно хранится в поле `leftChild`.
3. **Запуск Broad-Phase поиска:** используя подготовленные данные, поток запускает
   [алгоритм параллельного обхода дерева BVH (Broad-Phase)](#алгоритм-параллельного-обхода-дерева-bvh-broad-phase),
   начиная с корневой ноды (`In_RootNodeIndex[0]`, записанного `CS_FinalizeBVHIterationArgs`).
   Найденные пары-кандидаты пишутся через `EmitPair` в `Out_CandidatePairs` с дедупликацией
   `myLeafIdx < otherObjId` и защитой от переполнения буфера по `MaxPairsCapacity`.

## 8) Narrow-Phase: GJK и физический отклик

После broadphase (grid-based `TouchCheck` или BVH `CS_TraverseBVH`) для каждой пары
AABB-кандидатов выполняется точная проверка геометрии:

1. **`СontactСheck`** (`СontactСheck.hlsl`) — принимает два `objId` из `ObjectBuffer`, повторно
   (уже точно, не грубо) проверяет пересечение их мировых AABB через `CheckAABBCollision3D`. Если
   AABB пересекаются, извлекает `objBufferIndex` каждого объекта, число вершин их мешей
   (`MeshBuffer[...].vertexCount`) и запускает `GetClosestPoints3D`.
2. **`GetClosestPoints3D` (GJK)** (`GJK.hlsl`) — итеративный (до 16 итераций) алгоритм
   Gilbert–Johnson–Keerthi для выпуклых мешей: строит симплекс (точка → отрезок → треугольник →
   тетраэдр) в пространстве разности Минковского через опорные функции `SupportShape3DAB`,
   на каждой итерации проецирует начало координат на текущий симплекс и редуцирует его. При
   попадании тетраэдра "вокруг" начала координат (`intersects = true`) находит грань с минимальной
   глубиной проникновения и возвращает `pointA`, `pointB`, `normal`, `contactPoint`, `distance = 0`.
3. **`ComputePhysicsResponse`** (`СreatMovementTask.hlsl`) — принимает результат GJK и разрешает
   столкновение импульсным методом:
   - **Позиционная коррекция** (метод Баумгарте) — расталкивает объекты пропорционально глубине
     проникновения за вычетом допуска (`slop = 0.01`), пропорционально обратным массам.
   - **Нормальный импульс отскока** — считается с учётом инверсных тензоров инерции
     (`GetInverseInertiaTensor`, диагональная аппроксимация по описанному AABB) и коэффициента
     `restitution` (гасится до 0 при малых относительных скоростях, порог `0.15` м/с).
   - **Тангенциальный импульс (трение)** — ограничивается по закону Кулона: сравнивается требуемый
     импульс для полной остановки скольжения с `impulseMagnitude * muStatic`/`muDynamic`
     (комбинированные коэффициенты трения пары объектов).
   - Итоговый импульс применяется напрямую к `velocity`/`angularVelocity` обоих объектов.

## Алгоритм Мортона (Z-кривая)

Процесс генерации 30-битного кода Мортона из мировых координат центра объекта состоит из четырех
последовательных этапов:

1. **Нормализация координат сцены** — из мировых координат центра объекта вычитается минимальная
   точка сцены (`SceneMin`). Результат умножается на `SceneInvSize` (обратный размер сцены,
   рассчитанный на CPU как $\frac{1}{\text{SceneMax} - \text{SceneMin}}$). Этот шаг приводит
   координаты объекта к строгому диапазону [0.0, 1.0] относительно глобальных границ всей сцены.
   Данные о размерах сцены берутся из буфера параметров `SceneBounds`.
2. **Масштабирование и защита от переполнения (Clamp)** — полученные нормализованные значения
   умножаются на `1024.0f` и приводятся к целочисленному типу (`uint`). С помощью функций
   ограничения (`min`/`max`) координаты принудительно зажимаются в диапазоне от 0 до 1023. Это
   гарантирует, что координата по каждой из трех осей займет ровно 10 бит в памяти, что
   предотвращает выход за границы координатной сетки 1024³ и порчу данных на следующих этапах.
3. **Параллельное «раздвигание» битов** — каждое 10-битное число обрабатывается специальной
   функцией (`ExpandBits`) для создания «пустот» под биты других осей. Она преобразует сплошной
   ряд битов вида `abcdefghij` в разреженную строку вида `a00b00c00d00e00f00g00h00i00j` (где между
   каждым значащим битом остаются два пустых нуля). Для достижения максимальной скорости на GPU
   этот процесс реализован без медленных циклов: вместо них используются математические операции
   умножения на фиксированные «магические числа» и побитовые маски И (`&`).
4. **Сборка кода через перемежение битов (Interleaving)** — разреженные цепочки битов каждой оси
   сдвигаются влево на фиксированный шаг, чтобы занять свои уникальные позиции в итоговом
   регистре: координата X остается на месте (без сдвига), Y смещается влево на 1 бит, Z — на 2
   бита. Все три смещенные цепочки объединяются побитовым ИЛИ (`|`). На выходе получается единый
   30-битный код Мортона, в котором биты чередуются по паттерну фрактальной Z-кривой:
   `... Z Y X Z Y X`.

**Итог:** сгенерированный код вместе с исходным ID объекта записывается в буфер пар, который далее
передается на этап сортировки.

## Алгоритм параллельного обхода дерева BVH (Broad-Phase)

**Цель:** быстро найти все пересекающиеся пары объектов, избегая проверки «каждый с каждым»
(сокращение сложности с $O(N^2)$ до $O(N \log N)$).

#### Как это работает:
1. **Распараллеливание:** видеокарта запускает отдельный поток для каждого объекта (листа дерева).
   Каждый поток ищет столкновения только для своего объекта.
2. **Инициализация:** поток берет ограничивающий бокс (AABB) своего объекта и кладет в локальный
   стек индекс корня дерева (самую большую коробку).
3. **Цикл обхода (пока стек не пуст):**
   1) **Извлечение:** поток достает из стека индекс узла и читает его данные.
   2) **Грубая отсечка (AABB тест):** если бокс узла **не пересекается** с боксом нашего объекта,
      поток отбрасывает этот узел и всю его ветку (`continue`).
   3) **Если узел — ветка:** поток берет индексы левого и правого «ребенка» этой ветки и
      записывает их в стек для проверки на следующих шагах.
   4) **Если узел — лист (другой объект):** поток проверяет ID. Чтобы избежать дубликатов (не
      проверять пару $A \leftrightarrow B$ дважды), пара регистрируется только если ID текущего
      объекта меньше ID найденного — точная геометрическая проверка (GJK) выполняется уже за
      пределами этого кернела, в следующем шаге пайплайна.
4. **Завершение:** когда стек пустеет, поток завершает работу.
